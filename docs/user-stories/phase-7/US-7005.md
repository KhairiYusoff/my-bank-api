# US-7005 — Customer Sees Account Type Rules and Limits in Portal

**Phase:** 7
**Repos:** `my-bank-customer`, `my-bank-api`
**Epic:** Account Type Differentiation
**Status:** ✅ Completed
**Depends on:** US-7001 (account type enum must be lowercase in DB before this renders correctly)

---

## Revision Notes (v2)

Original spec had three problems that were corrected before implementation:

1. **Wrong business rule** — `savings: monthlyWithdrawals: "4 per month"` was carried over from US-7002 (Reg D), which was dropped. No account type has a monthly withdrawal cap in this system.
2. **FE hardcoded limits** — original spec made `accountLimits.ts` in the FE the "single source of truth". This creates a dual-maintenance problem: limit values already live in `transaction.service.js` on the BE. If BE values change, FE silently shows stale data. Corrected to: BE exposes a `GET /accounts/limits` endpoint that reads from the same constants the service uses.
3. **Wrong UX pattern** — a full static "Account Rules" card section is not how real banking apps surface limits. Customers only need to see limits at the point of action. Corrected to: ⓘ tooltip on the account type chip (passive discovery) + contextual hint below the amount field on transaction pages (active, just-in-time).

---

## Value Statement

As a customer, I want to understand the limits on my account before a transaction is rejected — through a tooltip on my account type and a hint on the transaction form — so I am not surprised.

---

## Background

After US-7001 enforces rules server-side, customers receive errors like "Transfer amount exceeds the RM5,000 single transfer limit". Without contextual UI surfacing these limits, the experience is confusing. Limits should appear at the two moments customers need them: when they're curious about their account type, and when they're about to enter an amount.

The limit values are already defined as constants in `transaction.service.js` (`MAX_SINGLE_TRANSFER`, `DAILY_TRANSFER_LIMIT`). These are the single source of truth — the BE endpoint reads from them.

## Screen Changes

### 1. AccountDetailsPage — Account Type Chip with ⓘ Tooltip

Below `GradientTitle "Account Details"` and above `BalanceCard`, a small chip shows the account type. Hovering/tapping the ⓘ icon opens a tooltip:

```
  [Savings  ⓘ]

  Tooltip:
  ┌─────────────────────────────────┐
  │  Daily transfer limit  RM10,000 │
  │  Max single transfer   RM5,000  │
  │  Overdraft             No       │
  │  Min withdrawal        RM10     │
  └─────────────────────────────────┘
```

For Fixed Deposit:

```
  Tooltip:
  ┌──────────────────────────────────────┐
  │  Transfers             Not permitted │
  │  Withdrawals           At maturity   │
  │  Overdraft             No            │
  └──────────────────────────────────────┘
```

### 2. WithdrawPage — Contextual Hint Below Amount Field

After the customer selects an account, the helperText below the amount input changes to show the account's limit:

```
  Amount
  [ 500.00                              ]
  Min: RM10.00  •  No upper limit for withdrawals
```

   ```js
   const ACCOUNT_LIMITS = {
     savings: {
       dailyTransferLimit: 10000,
       maxSingleTransfer: 5000,
       overdraftEligible: false,
       minWithdrawal: 10,
       transfersAllowed: true,
     },
     current: {
       dailyTransferLimit: 20000,
       maxSingleTransfer: 10000,
       overdraftEligible: true,
       minWithdrawal: 10,
       transfersAllowed: true,
     },
     business: {
       dailyTransferLimit: 50000,
       maxSingleTransfer: 20000,
       overdraftEligible: true,
       minWithdrawal: 10,
       transfersAllowed: true,

       dailyTransferLimit: null,
   ```

### FE-1: `useGetAccountLimitsQuery` in `accountsApi.ts`

1. New query added to `accountsApi`:
   ```ts
   getAccountLimits: builder.query<AccountLimitsResponse, void>({
     query: () => "/accounts/limits",
     providesTags: ["Account"],
   });
   ```
2. `AccountLimitsResponse` and `AccountTypeLimits` types defined inline in the API file (single use, no separate type file needed)
3. Hook exported: `useGetAccountLimitsQuery`

### FE-2: `AccountTypeChip` Component

1. New file: `src/features/accounts/components/AccountTypeChip.tsx`
2. Props: `accountType: string`, `overdraftLimit?: number`, `limits: AccountTypeLimits | null`
3. Renders a MUI `Chip` with the account type label + `InfoOutlined` icon as `deleteIcon` (or `icon`)
4. MUI `Tooltip` wraps the ⓘ icon — content is a compact list of the relevant limits from the `limits` prop
5. If `limits` is null (unknown type), renders a plain Chip with no tooltip
6. Overdraft row: if `limits.overdraftEligible && overdraftLimit > 0` → `RM{overdraftLimit}`, if eligible but 0 → `Not set`, if not eligible → `No`

### FE-3: `AccountDetailsPage.tsx` Updates

1. Calls `useGetAccountLimitsQuery()` — cached globally after first call
2. Derives `limits = data?.data?.[account?.accountType] ?? null`
3. Removes `AccountRulesCard` import and render
4. Adds `AccountTypeChip` below `GradientTitle` and above `BalanceCard`, passing `accountType`, `overdraftLimit`, `limits`
5. Router state and `useGetAccountsQuery` fallback (from previous implementation) are retained

### FE-4: `WithdrawPage.tsx` — Contextual Hint

1. Calls `useGetAccountLimitsQuery()` and `useGetAccountsQuery()` (already called via `useWithdrawForm`)
2. After the customer selects an account from the dropdown, reads the selected account's `accountType` from `accountsResponse?.data`
3. Derives limits for that type from the query result
4. The amount field `helperText` changes dynamically:
   - No account selected: `"Enter the amount to withdraw"`
   - Account selected, no error: `"Min: RM10.00"` (fixed minimum, universal rule)
   - Validation error present: shows error message as before (error takes priority)

### FE-5: Cleanup — Remove Stale Files

1. `src/features/accounts/utils/accountLimits.ts` — delete (replaced by BE endpoint)
2. `src/features/accounts/components/AccountRulesCard.tsx` — delete
3. Remove `AccountRulesCard` export from `components/index.ts`

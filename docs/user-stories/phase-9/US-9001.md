## Value Statement

As the `AccountService`, I want a unified, product-aware provisioning flow that enforces product-specific rules (min balance, lock period, KYC level) so that Current, Business, and Fixed Deposit accounts cannot be opened without banker review and all required business data.

---

## Background

Currently, the `onboarding` module auto-creates a `savings` account on customer verification. That remains the only instant-provision path. Product-specific provisioning (Current, Business, FD) lacks:

1. Product-specific validation (min balance, FD lock parameters).
2. Approval workflow (Current/Business/FD require banker review).
3. Immutable product metadata on approval (maturity date, principal, interest rate).

**Design decision — no new collection.** Pending requests are `Account` documents with `status: pending_approval`. Approval transitions the same document to `active` and fills in computed fields. There is no `AccountRequest` model.

## Acceptance Criteria

### BE-1: Account Request (`POST /api/accounts/request`)

**Auth:** Customer only.

| Check | Rule | Error message | HTTP |
|---|---|---|---|
| 1 | `type` is `current`, `business`, or `fixed_deposit` | "Account type requires banker approval" | 400 |
| 2 | `amount < MIN_OPENING_BALANCE[type]` | "Initial deposit amount below minimum for {type}" | 400 |
| 3 | `type === 'fixed_deposit'` | Require `lockPeriod` (1/3/6/12) + `linkedAccount` (account number) | 400 |
| 4 | `type === 'business'` | Require `companyRegistrationDoc` (mocked string URL) | 400 |
| 5 | `linkedAccount` (FD only) | Must exist, belong to requester, `status === 'active'` | 404 / 403 |

**Resulting state:** One `Account` document created with:

- `status: pending_approval`
- `accountType`, `balance` (= initial `amount` / principal), product fields from request
- `accountNumber` assigned at request time via `generateAccountNumber()` — see `business-rules.md` §1.5 (account exists but is not operational until approved)
- No transactions permitted while `pending_approval`

> Savings accounts are **not** requested via this endpoint — they are still provisioned on onboarding verification.

### BE-2: List Pending Requests (`GET /api/accounts/account-requests`)

**Auth:** Banker only.

- Returns paginated `Account` documents where `status === 'pending_approval'`
- Populates customer name/email from `user` ref

### BE-3: Approve Request (`POST /api/accounts/account-requests/:id/approve`)

**Auth:** Banker only.

1. Load `Account` by `_id`; reject if not `pending_approval` (400).
2. For FD: compute `maturityDate` (`dateOpened + lockPeriod months`), set `interestRate` from lock-period table in `business-rules.md` §3.2.
3. For FD: debit `linkedAccount` by principal amount (MongoDB session — atomic).
4. Set `status: active`, `dateOpened: now` (or keep original request date — pick one, document in code).
5. Log `APPROVE_ACCOUNT_REQUEST` in `ActivityLog`.

### BE-4: Reject Request (`POST /api/accounts/account-requests/:id/reject`) — optional but recommended

**Auth:** Banker only.

- Set `status: closed` (or delete doc — prefer `closed` for audit trail).
- Log rejection in `ActivityLog`.

## Technical Tasks

1. **Task 0:** Status enum migration (see Prerequisites).
2. **Model:** Extend `Account` schema:
   - Status enum: `pending_approval`, `active`, `dormant`, `suspended`, `pending_closure`, `closed`
   - FD fields: `lockPeriod`, `maturityDate`, `linkedAccount` (ref Account), `principal`, `autoRenew` (default false)
   - Business field: `companyRegistrationDoc`
3. **Constants:** Add `MIN_OPENING_BALANCE` to `shared/constants/` (values from `business-rules.md` §1.2).
4. **Utility:** Add `shared/utils/generateAccountNumber.js` per `business-rules.md` §1.5 (uses atomic `Counter` for guaranteed uniqueness plus cryptographically secure random numbers to prevent enumeration attacks); replace inline `MYB${Date.now()}` in `onboarding.service` and `account.service.createAccount`.
5. **Service (`account.service.js`):**
   - `requestAccount(userId, data)` — validates + creates `pending_approval` Account
   - `getPendingAccountRequests(query)` — banker list
   - `approveAccountRequest(accountId, bankerId)` — activates + FD debit leg
   - `rejectAccountRequest(accountId, bankerId, reason)` — optional
6. **Routes** (all in `account.routes.js`; register `/request` and `/account-requests` **before** `/:accountNumber`):
   - `POST /api/accounts/request` — customer
   - `GET /api/accounts/account-requests` — banker
   - `POST /api/accounts/account-requests/:id/approve` — banker
   - `POST /api/accounts/account-requests/:id/reject` — banker (recommended)
7. **Guards:** All money operations (`deposit`, `withdraw`, `transfer`) must reject `status !== 'active'`.

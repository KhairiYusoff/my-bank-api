# US-6004 — Admin Views Account Transaction History

**Phase:** 6 (addendum)
**Repos:** `my-bank-api`, `my-bank-admin-portal`
**Epic:** Admin Detail Pages
**Status:** 🟡 Ready for Development
**Depends on:** US-6003 (AccountDetailPage must exist — this page is navigated to from it)

---

## Value Statement

As an admin or banker, I want to click "View Transactions" on an account detail page and see a dedicated, paginated list of all transactions for that specific account, so I can investigate account activity in full context without manually filtering the global transactions list.

---

## Background

The global transactions page at `/transactions` shows all transactions across all accounts with no filtering. When an admin/banker is already viewing a specific account at `/accounts/:accountNumber`, they need a way to drill into that account's transaction history without losing the account context.

The BE endpoint `GET /transactions/account/:accountNumber` already exists and supports `admin` and `banker` roles. The FE does not yet have a query for it and there is no dedicated page.

The "View Transactions" button was temporarily removed from AccountDetailPage (it was pointing to the wrong destination). This story restores it with the correct implementation.

## Acceptance Criteria

### BE-1: No Changes Required

`GET /transactions/account/:accountNumber` already exists and supports `admin` and `banker` roles. No BE work needed.

### FE-1: RTK Query — New Endpoint

1. Add `getAccountTransactions` query to `transactionsApi.ts`:
   - `GET /transactions/account/:accountNumber`
   - Params: `{ accountNumber: string; page?: number; limit?: number; sort?: "asc" | "desc" }`
   - `providesTags: [{ type: "Transactions", id: accountNumber }]`
2. Export `useGetAccountTransactionsQuery`

### FE-2: New Page

1. New file: `src/features/accounts/pages/AccountTransactionsPage.tsx`
2. Reads `accountNumber` from `useParams`
3. Reads account context from `location.state` (passed from AccountDetailPage) to render the sub-header (account number, holder name, account type, status chip) — falls back to `—` if state absent (direct URL)
4. Fetches transactions via `useGetAccountTransactionsQuery({ accountNumber, page, limit })`
5. Renders paginated table with columns: Date, Description, Type, Amount, Status
6. Amount: green `+RM X,XXX.XX` for credits (deposit, airdrop), red `-RM X,XXX.XX` for debits (withdrawal, transfer)
7. Clicking any row opens `TransactionDetailDrawer` (import from `@/features/transactions/components`)
8. Loading state: `CircularProgress` centred
9. Empty state: `Alert severity="info"` — "No transactions found for this account."
10. Error state: `Alert severity="error"`

### FE-3: Breadcrumb

1. Use MUI `Breadcrumbs` component at the top of the page (above the page title)
2. Structure: `Accounts` → `{accountNumber}` → `Transactions`
3. `Accounts` links to `/accounts`
4. `{accountNumber}` links to `/accounts/:accountNumber`
5. `Transactions` is plain text (current page — not a link)
6. Replace the plain "Back to Accounts" back button with the breadcrumb — no separate back button needed

### FE-4: Wire AccountDetailPage Button

1. In `AccountDetailPage.tsx`, restore the "View Transactions" button in the header actions:
   - `Button variant="outlined" size="small"`
   - Navigates to `/accounts/${account.accountNumber}/transactions`
   - Passes `state: { account }` so AccountTransactionsPage can render the sub-header without a separate API call

### FE-5: Routing

1. New route in `routes.tsx`: `/accounts/:accountNumber/transactions` → `AccountTransactionsPage`, `requiresAuth: true`
2. Lazy-loaded: `const AccountTransactionsPage = lazy(() => import("@/features/accounts/pages/AccountTransactionsPage"))`

---

## Page Location — Why `features/accounts/` Not `features/transactions/`

The page lives in `features/accounts/pages/` because:

- The URL context is account-centric (`/accounts/:accountNumber/transactions`)
- Navigation originates from AccountDetailPage
- The breadcrumb is rooted at Accounts

The _data_ comes from `features/transactions/store/transactionsApi.ts` — that is correct. Domain of the URL/navigation context determines page location, not data source.

## Out of Scope

- Filtering transactions by type/status/date on this page — add as a future enhancement
- Exporting transactions — covered by Phase 11 (Statements)
- Pagination beyond client-side — the existing `getAccountTransactions` BE endpoint supports server-side pagination via `page` + `limit` params, use it

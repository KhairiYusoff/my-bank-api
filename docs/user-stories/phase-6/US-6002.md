# US-6002 — Admin Views Staff Profile (Detail Page)

**Phase:** 6
**Repos:** `my-bank-api`, `my-bank-admin-portal`
**Epic:** Admin Detail Pages
**Status:** ✅ Completed
**Depends on:** US-6001 (shares `DetailSection` component — build US-6001 first)

---

## Value Statement

As an admin, I want to click on any staff member in the staff list and see their full profile — role, account status, verification state, and audit of when they were created — so I can manage staff access with full context rather than acting blind from a table row.

---

## Background

Staff are created by admin via `POST /admin/create-staff` with only `name`, `email`, `password`, and `role`. They are immediately flagged `isVerified: true` and `isProfileComplete: true` without completing any self-service profile setup. This means staff records are intentionally minimal today.

Staff do **not** have: phone number, address, KYC data, employment info, next of kin, or identity number. These are customer-only fields. Staff profile setup (US-8002, Phase 8) will add a first-login flow for staff in the future.

The staff detail page therefore shows only what actually exists. It does **not** show `applicationStatus` — that is a customer onboarding field that is meaningless for staff and must be hidden.

There is no `GET /admin/staff/:staffId` endpoint today. This story adds it.

## Acceptance Criteria

### BE-1: New API Endpoint

1. `GET /admin/staff/:staffId` added to `admin.routes.js`
2. Allowed roles: `admin` only (staff list is admin-only per RBAC matrix)
3. Returns the full User document for the given `_id`, excluding `password` and `refreshToken`
4. Returns `404` with `{ success: false, message: "Staff not found" }` if ID does not exist or user role is not `banker` or `admin`
5. Response follows the `success()` utility format: `{ success: true, message: "Staff fetched", data: { ...user } }`
6. Activity logged via `activityLogger("VIEW_STAFF_PROFILE", "Admin viewed staff profile")`
7. Implementation follows Route → Controller → Service pattern

### BE-2: Service Method

1. New `getStaffById(staffId)` method in `admin.service.js`
2. Uses `User.findOne({ _id: staffId, role: { $in: ["banker", "admin"] } }).select("-password -refreshToken")`
3. Throws `404` if not found

### FE-1: List Page — Actions Simplified

1. Inline Role `<Select>` removed from the Role cell in `StaffPage.tsx`
2. Role displayed as plain text instead
3. `Delete` icon button removed from the Actions cell — Delete moves to the detail page
4. `[View →]` button added — navigates to `/staff/:id` via React Router `useNavigate`
5. Actions column is now a single button — adjust column width accordingly

### FE-2: Routing

1. New route registered in `routes.tsx`: `/staff/:id` → `StaffDetailPage`
2. Route is auth-protected (`requiresAuth: true`)
3. On navigation from the list, staff object passed as router state (`state: { staff }`)
4. On direct URL access or refresh, page calls `GET /admin/staff/:id` to hydrate

### FE-3: New RTK Query Endpoint

1. `getStaffById` query added to `staffApi.ts`:
   - `GET /admin/staff/:id`
   - `providesTags: [{ type: "Staff", id }]`
2. `useGetStaffByIdQuery` hook exported

### FE-4: Detail Page — Layout

1. New file: `src/features/staff/pages/StaffDetailPage.tsx`
2. Page header: staff name (h5), `StatusChip` for account status, role label
3. Header action buttons: `Change Role` (opens `ChangeRoleModal`), `Manage Status` (opens `ChangeStatusModal` — reused from US-6001), `Delete` (opens `ConfirmationDialog`)
4. Back link: `← Back to Staff` navigates to `/staff`
5. Content split into labelled sections using the shared `DetailSection` component from US-6001
6. Sections: Account Info, Preferences
7. `applicationStatus` field is **never displayed** — it is a customer onboarding artifact irrelevant to staff
8. `View Full Activity Log` button opens `UserActivityModal` (already exists, pass `userId`)

### FE-5: Change Role Modal

1. New file: `src/features/staff/components/ChangeRoleModal.tsx`
2. Displays current role, radio buttons for `banker` / `admin`
3. Current role option is disabled (greyed out)
4. Warning `Alert` shown when selecting `admin`: "This grants full system access including staff management."
5. Confirm button disabled until a different role is selected
6. On confirm: calls `PUT /admin/staff/:staffId` with `{ role: newRole }` — reuses existing `useUpdateStaffMutation`
7. Admin cannot change their own role (guard: compare `staff._id` with logged-in user `_id` — disable Change Role button entirely if same person)

### FE-6: Reuse `ChangeStatusModal`

1. `ChangeStatusModal` built in US-6001 (actually already built in Phase 3 hotfix) is reused directly
2. No modifications required — it already accepts `user: User | null` and works for any user with a `status` field
3. On confirm: calls `PUT /admin/staff/:staffId` with `{ status: newStatus }` via `useUpdateStaffMutation`

### FE-7: Loading & Error States

1. Same pattern as US-6001: `CircularProgress` on load, `Alert` on error, `Alert` on 404 with back link

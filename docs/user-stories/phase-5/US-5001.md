# US-5001 — Transaction Detail Receipt

**Phase:** 5
**Epic:** Transaction Detail Enrichment
**Status:** 📝 Ready for Development
**Story Points:** 8

---

## Value Statement

As a customer, I want to tap on any transaction to see a full receipt — with the reference number, counterpart name, and my balance after — so that I can verify the details or quote a reference when disputing.

---

## Background

The Phase 1 refactor replaced `fromAccountNumber`/`toAccountNumber` fields with a single `account: ObjectId` ref. This lost all counterpart info. Currently the detail view shows the same 5 fields as the list row — no reference number, no recipient name, no running balance. This is a UX failure and a dispute risk.

All new fields must be **captured at write time** inside the existing MongoDB session. Never recomputed on read.

## New Fields on Transaction Model

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `reference` | String | null | `TXN-YYYYMMDD-XXXXX` — unique, generated at write time |
| `counterpartAccount` | String | null | Account number of the other party |
| `counterpartName` | String | null | Masked name of other party, stored pre-masked |
| `balanceAfter` | Number | null | Account balance snapshot after transaction completes |
| `fee` | Number | 0 | Fee charged. Zero for all transactions in Phase 5 |

All fields sparse/nullable so existing documents don't break.

---

## Acceptance Criteria

### 1. Reference Number (`reference`)

1. Format: `TXN-YYYYMMDD-XXXXX` — date in UTC, 5-digit zero-padded daily sequence
2. Sequence is atomic — use a `Counter` collection: `{ _id: "txn_20260529", seq: 142 }`, incremented with `findOneAndUpdate + $inc`
3. If no counter document exists for today, create it with `seq: 1`
4. `reference` field has a sparse unique index — enforces uniqueness, allows existing null documents
5. Generated for every transaction type: transfer, deposit, withdrawal, airdrop, fee
6. Never editable after creation

### 2. Counterpart Fields (`counterpartAccount`, `counterpartName`)

1. Both fields populated at write time in `transferFunds` — on **both** the debit and credit records
2. Debit record (sender): `counterpartAccount` = recipient's account number, `counterpartName` = masked recipient name
3. Credit record (recipient): `counterpartAccount` = sender's account number, `counterpartName` = masked sender name
4. For deposit, withdrawal, airdrop: `counterpartName = "MyBank"`, `counterpartAccount = null`

**Name masking rule** (applied before storing):
- Keep first word in full, take first char of second word + `****`
- `"Ahmad Khalid"` → `"Ahmad K****"`
- `"Siti Rahayu Binti Hassan"` → `"Siti R****"` (ignore words after second)
- Single name `"Salmah"` → `"S****"`

**Account number masking** (applied at API response layer, not stored):
- Customer role: `"MYB-001-234567"` → `"MYB****7"` (first 3 chars + `****` + last char)
- Admin/banker role: full account number returned unmasked

### 3. Balance After (`balanceAfter`)

1. Captured immediately after balance update within the same MongoDB session
2. In `transferFunds`: debit record gets sender's balance after deduction; credit record gets recipient's balance after addition
3. In `deposit`, `withdraw`, `airdrop`: balance after the operation
4. Stored as a Number, 2 decimal precision

### 4. API Responses

1. All new fields included in `GET /transactions/account/:accountNumber` (list) and `GET /transactions/:transactionId` (detail)
2. `POST /transactions/transfer` response body includes `reference` of both created transaction records
3. Customer role: `counterpartName` as stored (already masked), `counterpartAccount` masked at response layer
4. Admin/banker role: full unmasked name (looked up from User model at response time) + full account number

### 5. UI — Customer Portal

**Transaction list:**
1. Each row is tappable — opens receipt drawer/modal
2. Counterpart name shown as secondary line on transfer rows (e.g. `Ahmad K****`)
3. Reference shown as a small muted line below the date

**Receipt view:**
1. Direction badge: `TRANSFER SENT` / `TRANSFER RECEIVED` / `DEPOSIT` / `WITHDRAWAL`
2. Amount displayed prominently
3. All fields from the table in "Screen" section above
4. If a field is null (old pre-Phase-5 transaction): show `"—"` for reference/counterpart, omit `balanceAfter` row entirely
5. Fee shown as `RM0.00` even when zero — builds trust

### 6. UI — Admin Portal

1. Transaction detail panel shows all fields **unmasked**: full name, full account number
2. Admin additionally sees `deviceInfo.ip` and `deviceInfo.userAgent` if populated (Phase 5 nice-to-have)

### 7. Error State

1. If receipt fails to load: show `"Unable to load receipt. Please try again."` with retry
2. Retry calls `GET /transactions/:transactionId`

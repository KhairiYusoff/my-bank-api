# US-5001 — Transaction Model Enrichment & API

**Phase:** 5
**Repo:** `my-bank-api`
**Epic:** Transaction Enrichment
**Status:** 🟡 Ready for Development
**Depends on:** —

---

## Value Statement

As an engineer, I want every transaction record to capture complete contextual data at write time — reference number, counterpart, both balance snapshots, channel, device, timing, fraud scaffolding, and reversal markers — so that customer portals can render full receipts, the fraud engine has raw signals to work with, and reversals can be implemented in a future phase without a migration.

---

## Background

Current `Transaction` model has 7 fields: `account`, `type`, `amount`, `description`, `status`, `performedBy`, `date`. This is a bare ledger entry — no receipt data, no audit trail, no fraud signals.

The Phase 1 refactor removed `fromAccountNumber`/`toAccountNumber`, losing all counterpart info. That data must be re-captured at write time inside the existing MongoDB session. It cannot be reconstructed on read.

All fields added in this story must have safe defaults (`null`, `0`, `"MYR"`) so existing documents remain valid without migration.

## New Fields on Transaction Model

| Field                        | Type     | Default | Description                                                                                    |
| ---------------------------- | -------- | ------- | ---------------------------------------------------------------------------------------------- |
| `reference`                  | String   | null    | `TXN-YYYYMMDD-XXXXX` — globally unique, generated atomically                                   |
| `counterpartAccount`         | String   | null    | Raw account number of the other party (never masked at rest)                                   |
| `counterpartName`            | String   | null    | Pre-masked name stored at write time — returned to customers                                    |
| `counterpartNameRaw`         | String   | null    | Unmasked full name stored at write time — returned to admin/banker only, never to customers    |
| `balanceBefore`              | Number   | null    | Account balance snapshot immediately **before** this transaction                               |
| `balanceAfter`               | Number   | null    | Account balance snapshot immediately **after** this transaction                                |
| `fee`                        | Number   | 0       | Fee charged. Zero for all Phase 5 transactions                                                 |
| `currency`                   | String   | `"MYR"` | Currency at transaction time. Future-proofs for FX                                             |
| `memo`                       | String   | null    | Optional customer-written note ("paid rent", "dinner"). Max 255 chars                          |
| `channel`                    | String   | `"web"` | How the transaction was initiated — see enum below                                             |
| `deviceInfo.ip`              | String   | null    | IP address of the initiating request                                                           |
| `deviceInfo.userAgent`       | String   | null    | Browser/client fingerprint                                                                     |
| `processingTime.submittedAt` | Date     | null    | When the request hit the server                                                                |
| `processingTime.completedAt` | Date     | null    | When the DB write committed                                                                    |
| `isNewRecipient`             | Boolean  | null    | Was this the first-ever transfer to this recipient? Fraud signal — only knowable at write time |
| `twoFactorVerified`          | Boolean  | null    | Was 2FA passed? Reserved — always `null` until 2FA is implemented                              |
| `riskFlags`                  | Array    | `[]`    | Empty now. Fraud engine writes here in a future fraud phase e.g. `[{ flag: "new_device", at: Date }]`      |
| `isReversed`                 | Boolean  | false   | Flipped to `true` on the original record when reversed in a future reversal phase                          |
| `reversalOf`                 | ObjectId | null    | Populated on the reversal record only — points back to the original transaction                             |

**`channel` enum:** `"web"`, `"mobile"`, `"branch"`, `"api"`, `"system"`

- `"web"` = customer-initiated from portal
- `"branch"` = banker-initiated deposit/withdrawal
- `"system"` = cron jobs, airdrop, admin-initiated operations
- `"mobile"`, `"api"` = **reserved** — not produced by any current code path

**`channel` is always derived server-side from `req.user.role` — never trusted from client input:**

| `req.user.role` | `channel`   |
| --------------- | ----------- |
| `customer`      | `"web"`     |
| `banker`        | `"branch"`  |
| `admin`         | `"system"`  |
| cron / system   | `"system"`  |

## Acceptance Criteria

### 1. Schema Changes

1. All 19 fields added to `TransactionSchema` with the defaults from the table above
2. `reference` has a `sparse: true` unique index — enforces uniqueness, allows existing `null` documents
3. `counterpartAccount` has a regular index — required for `isNewRecipient` history check performance
4. `reversalOf` has a `sparse: true` index — allows null, enables fast lookup of reversal chain in a future reversal phase
5. `memo` has `maxlength: 255` at schema level
6. `deviceInfo`, `processingTime` are nested objects (not subdocuments) — no `_id`
7. `riskFlags` default is `[]` — no subdocument schema enforced (fraud engine defines shape in a future fraud phase)
8. `Account.currency` default is already `"MYR"` — **no change needed** (fixed in commit `1dc0e67` before this story was written)
9. Existing documents with no new fields remain valid — no migration required. **Important:** `.lean()` queries return `undefined` (not `null`) for new fields on old documents. All consuming code must use `??` (nullish coalescing), not strict `=== null` checks

### 2. Reference Number Generation

1. Format: `TXN-YYYYMMDD-XXXXX` — date in **MYT (UTC+8)**, 5-digit zero-padded daily sequence. Malaysian time ensures the reference date always matches the customer's receipt date, including late-night transactions
2. Uses a `Counter` collection: `{ _id: "txn_20260529", seq: 142 }` — atomic `findOneAndUpdate` with `$inc: { seq: 1 }` and `upsert: true`
3. Utility: `getNextReference()` in `src/shared/utils/reference.js` — computes current MYT date internally, returns formatted string e.g. `"TXN-20260531-00001"`
4. **If `getNextReference()` throws for any reason, the entire transaction must abort** — do not continue with `reference = null`. Wrap the call in try/catch and rethrow before the session starts
5. Generated for every transaction type: transfer, deposit, withdrawal, airdrop
6. Never editable after creation — no update path exposed

### 3. Name Masking

1. Utility: `maskName(fullName)` in `src/shared/utils/maskName.js`
2. Rules:
   - Keep first word in full, take first char of second word + `****`
   - `"Ahmad Khalid"` → `"Ahmad K****"`
   - `"Siti Rahayu Binti Hassan"` → `"Siti R****"` (words after second ignored)
   - Single word: `"Salmah"` → `"S****"`
3. Stored pre-masked — masking happens once at write time, not on every read

### 4. Populating Fields — `transferFunds`

1. **Account reads happen inside the MongoDB session** — both `Account.findOne()` calls (sender and recipient) must execute after `session.startTransaction()`. Reading outside the session creates a concurrency gap where a parallel transfer could mutate balances between read and write, producing a stale `balanceBefore` and bypassing the balance check
2. Both debit and credit Transaction records get all applicable fields populated within the same session
3. Debit record (sender):
   - `counterpartAccount` = recipient's raw account number
   - `counterpartName` = `maskName(recipientUser.name)` — pre-masked, returned to customers
   - `counterpartNameRaw` = `recipientUser.name` — unmasked, returned to admin/banker only
   - `balanceBefore` = sender's balance **before** deduction (captured inside session, before mutation)
   - `balanceAfter` = sender's balance **after** deduction
   - `channel` = derived from `req.user.role` — **never from `req.body`** (see role→channel table above)
   - `deviceInfo.ip` = `req.ip`
   - `deviceInfo.userAgent` = `req.headers['user-agent']`
   - `processingTime.submittedAt` = set at service entry (before session)
   - `processingTime.completedAt` = set immediately before `session.commitTransaction()`
   - `isNewRecipient` = `true` if sender has no prior completed transfer to this `counterpartAccount`, else `false`. Query runs before the session (read-only): `Transaction.findOne({ performedBy: userId, counterpartAccount: toAccountNumber, status: "completed", type: "transfer" })`
   - `twoFactorVerified` = `null` (2FA not implemented yet)
   - `riskFlags` = `[]`
   - `isReversed` = `false`
   - `reversalOf` = `null`
4. Credit record (recipient): mirror with sender's details as counterpart; `isNewRecipient` = `null` on credit records (concept only applies to sender)
5. Both records share the same `reference` value — one reference per transfer pair

### 5. Populating Fields — `deposit`, `withdraw`, `airdrop`

1. `counterpartName = "MyBank"`, `counterpartNameRaw = "MyBank"`, `counterpartAccount = null`
2. `balanceBefore` = account balance before the operation (captured inside session, before mutation)
3. `balanceAfter` = account balance after the operation
4. `channel` — derived server-side from `req.user.role` — **never hardcoded per transaction type**:
   - `req.user.role === "customer"` → `"web"` (e.g. customer self-deposits)
   - `req.user.role === "banker"` → `"branch"` (e.g. banker-initiated deposit)
   - `req.user.role === "admin"` → `"system"` (e.g. airdrop)
5. `deviceInfo` and `processingTime` populated same as transfers
6. `isNewRecipient` = `null` (not applicable for non-transfer types)
7. `twoFactorVerified` = `null`, `riskFlags` = `[]`, `isReversed` = `false`, `reversalOf` = `null`

**For transaction LIST (`GET /transactions/all`) — batch name resolution:**

Do not perform N individual User lookups per page. Instead:
1. Collect all unique `counterpartAccount` values from the page result
2. One `User.find({ accountNumber: { $in: [...] } })` call to resolve names
3. Map results back to each transaction before building the response

> Note: with `counterpartNameRaw` now stored at write time, this batch lookup is only needed if you want to verify the account still exists (for the `[Account Deleted]` label). The name itself comes from `counterpartNameRaw` on the document — no User lookup needed for the name.

Controller maps service result to this explicit shape — do not return raw Mongoose documents:

```json
{
  "success": true,
  "message": "Transfer successful",
  "data": {
    "reference": "TXN-20260531-00001",
    "amount": 500,
    "balanceAfter": 1500.00,

    "counterpartName": "Ahmad K****",
    "date": "2026-05-31T14:30:00.000Z"
  }

```

- `counterpartAccount` masked (customer-facing endpoint)
- `balanceAfter` is the sender's new balance after the transfer
- Do not include `deviceInfo`, `riskFlags`, or other internal fields in this response

#### Pre-Phase-5 documents (old transactions with no new fields)

Old transactions fetched via `.lean()` return `undefined` for all new fields — not `null`. Example:

```json
{
  "_id": "664abc000000000000000001",
  "type": "transfer",
  "amount": -200,
  "description": "Transfer to MYB0000003",
  "status": "completed",
  "reference": undefined,
  "counterpartAccount": undefined,
  "counterpartName": undefined,
  "balanceBefore": undefined,
  "balanceAfter": undefined
}
```

All consuming code (this story's service layer and future FE stories US-5002/5003) must use `??` not `=== null`:
- ✅ `transaction.balanceAfter ?? "—"`
- ❌ `transaction.balanceAfter === null ? "—" : transaction.balanceAfter`

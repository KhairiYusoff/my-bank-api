# US-5001 — Transaction Model Enrichment & API

**Phase:** 5
**Repo:** `my-bank-api`
**Epic:** Transaction Enrichment
**Status:** 📝 Ready for Development
**Depends on:** —

---

## Value Statement

As an engineer, I want every transaction record to capture complete contextual data at write time — reference number, counterpart, running balance, channel, device, and timing — so that customer portals can render full receipts and the system has a fraud-ready audit trail from day one.

---

## Background

Current `Transaction` model has 7 fields: `account`, `type`, `amount`, `description`, `status`, `performedBy`, `date`. This is a bare ledger entry — no receipt data, no audit trail, no fraud signals.

The Phase 1 refactor removed `fromAccountNumber`/`toAccountNumber`, losing all counterpart info. That data must be re-captured at write time inside the existing MongoDB session. It cannot be reconstructed on read.

All fields added in this story must have safe defaults (`null`, `0`, `"MYR"`) so existing documents remain valid without migration.

---

## New Fields on Transaction Model

| Field | Type | Default | Description |
|---|---|---|---|
| `reference` | String | null | `TXN-YYYYMMDD-XXXXX` — globally unique, generated atomically |
| `counterpartAccount` | String | null | Raw account number of the other party (never masked at rest) |
| `counterpartName` | String | null | Pre-masked name stored at write time |
| `balanceAfter` | Number | null | Account balance snapshot immediately after this transaction |
| `fee` | Number | 0 | Fee charged. Zero for all Phase 5 transactions |
| `currency` | String | `"MYR"` | Currency at transaction time. Future-proofs for FX |
| `memo` | String | null | Optional customer-written note ("paid rent", "dinner") |
| `channel` | String | `"web"` | How the transaction was initiated — see enum below |
| `deviceInfo.ip` | String | null | IP address of the initiating request |
| `deviceInfo.userAgent` | String | null | Browser/client fingerprint |
| `processingTime.submittedAt` | Date | null | When the request hit the server |
| `processingTime.completedAt` | Date | null | When the DB write committed |

**`channel` enum:** `"web"`, `"mobile"`, `"branch"`, `"api"`, `"system"`
- `"system"` = cron jobs, airdrop, automated operations
- `"branch"` = banker-initiated deposit/withdrawal

## Acceptance Criteria

### 1. Schema Changes

1. All 12 fields added to `TransactionSchema` with the defaults from the table above
2. `reference` has a `sparse: true` unique index — enforces uniqueness, allows existing `null` documents
3. `deviceInfo` and `processingTime` are nested objects (not subdocuments) — no `_id`
4. `Account.currency` default corrected from `"USD"` → `"MYR"` (bug fix, same PR)
5. Existing documents with no new fields remain valid — no migration required

### 2. Reference Number Generation

1. Format: `TXN-YYYYMMDD-XXXXX` — date in UTC, 5-digit zero-padded daily sequence
2. Uses a `Counter` collection: `{ _id: "txn_20260529", seq: 142 }` — atomic `findOneAndUpdate` with `$inc: { seq: 1 }` and `upsert: true`
3. Utility: `getNextReference(date)` in `src/shared/utils/reference.js` — returns formatted string
4. Generated for every transaction type: transfer, deposit, withdrawal, airdrop
5. Never editable after creation — no update path exposed

### 3. Name Masking

1. Utility: `maskName(fullName)` in `src/shared/utils/maskName.js`
2. Rules:
   - Keep first word in full, take first char of second word + `****`
   - `"Ahmad Khalid"` → `"Ahmad K****"`
   - `"Siti Rahayu Binti Hassan"` → `"Siti R****"` (words after second ignored)
   - Single word: `"Salmah"` → `"S****"`
3. Stored pre-masked — masking happens once at write time, not on every read

### 4. Populating Fields — `transferFunds`

1. Both debit and credit Transaction records get all applicable fields populated within the same MongoDB session
2. Debit record (sender):
   - `counterpartAccount` = recipient's raw account number
   - `counterpartName` = `maskName(recipientUser.name)`
   - `balanceAfter` = sender's balance after deduction
   - `channel` = passed from controller (`req.body.channel` or default `"web"`)
   - `deviceInfo.ip` = `req.ip`
   - `deviceInfo.userAgent` = `req.headers['user-agent']`
   - `processingTime.submittedAt` = set at service entry
   - `processingTime.completedAt` = set immediately before session commit
3. Credit record (recipient): mirror of above with sender's details
4. Both records share the same `reference` value — one reference per transfer pair

### 5. Populating Fields — `deposit`, `withdraw`, `airdrop`

1. `counterpartName = "MyBank"`, `counterpartAccount = null`
2. `balanceAfter` = account balance after the operation
3. `channel`:
   - `deposit` → `"branch"` (banker-initiated)
   - `withdraw` → `"web"` (customer-initiated)
   - `airdrop` → `"system"` (admin-initiated)
4. `deviceInfo` and `processingTime` populated same as transfers

### 6. API Responses — Role-Based Masking

**Customer role (`GET /transactions/account/:accountNumber`, `GET /transactions/:id`):**
1. `counterpartName` returned as stored (already masked)
2. `counterpartAccount` masked at response layer: first 3 chars + `****` + last char (e.g. `"MYB****7"`)
3. `deviceInfo` omitted entirely
4. All other new fields returned as-is

**Admin / Banker role (same endpoints):**
1. `counterpartName` — looked up from User model at response time, returned unmasked
2. `counterpartAccount` — returned full, unmasked
3. `deviceInfo.ip` and `deviceInfo.userAgent` included
4. `processingTime` included

**Transfer response (`POST /transactions/transfer`):**
1. Response body includes `reference` (same value on both records)
2. Response body includes `balanceAfter` for the sender's account

### 7. Counter Model

1. `Counter` collection created: `src/shared/models/Counter.js`
2. Schema: `{ _id: String, seq: Number }`
3. No TTL — counter documents accumulate daily (`txn_20260529`, `txn_20260530`, …) — cleanup is a future ops task
